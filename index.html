The Einstein radius is not an augmentation

How I built a self-supervised foundation model for dark matter substructure, what worked, and the many things that did not.

Arnesh · September 2026 · Code · References

TL;DR

  • I pretrained one Vision Transformer on 87,525 unlabelled simulated lens images, froze it, and reused it for three tasks: substructure classification, axion mass regression and 2× super-resolution.
  • Normal self-supervised tricks like crop and zoom are physically wrong for lenses: zooming changes the Einstein radius, which measures the lens mass. So I replaced them with two lensing-aware loss terms on top of LeJEPA. I call the result Lens-LeJEPA.
  • With 100 labels per class the two terms add +11 accuracy points over the exact same model without them. With rank-stabilized LoRA the frozen encoder reaches 97.7% on full data while training only 11% of the weights.
  • It is not a win everywhere. The same terms hurt super-resolution (−3.6 dB) and do not help mass regression. I think one simple idea explains both the wins and the losses.

1. Why this problem

When a massive galaxy sits between us and a more distant galaxy, its gravity bends the light of the far one into arcs, and sometimes into a full ring. This is strong gravitational lensing. The exact shape of those arcs depends on how mass is spread inside the lens, including small clumps of dark matter that we cannot see directly. That makes lens images one of the very few ways to test dark matter on small scales.

Different dark matter models leave different marks. In cold dark matter (CDM) the main halo contains many small subhaloes. In models with an ultra-light axion, the dark matter behaves like a wave and forms vortex-like interference patterns. The DeepLense project asks: can a neural network tell these apart from the image alone?

Supervised networks already do this very well on simulations. The catch is labels. To label an image, a simulation first has to assume a dark matter model. And upcoming surveys like Euclid will give us huge numbers of lens images with no labels at all. That is exactly the setting where self-supervised learning (SSL) should help: learn from unlabelled images first, then use a small number of labels later.

But there is a problem with how SSL is usually done. Most methods learn by making two "views" of an image with random crops, zooms and colour changes, and then teaching the network that both views are the same thing. For a lens, a zoom is not harmless. It changes the apparent Einstein radius \(\theta_E\), the radius of the ring, and the mass inside the ring grows like \(\theta_E^2\). An encoder trained to ignore zoom is being trained to throw away a mass measurement. This point was first made by the LenSiam paper, and it became the starting point for my project.

2. The data

I used the public DeepLense simulations, made with lenstronomy. Each image has a lens galaxy in the centre and a background source that gets lensed. There are three classes: axion, CDM, and no substructure. The difference between classes is small: a slight change in the arcs, not a change in the overall ring.

DatasetSizeImagesHow I used it

Two facts about this data shaped my whole design. First, the lens is always in the centre and the simulated blur (the point spread function) is the same in every direction. So rotating the image by 90° or mirroring it gives an equally valid observation of the same system: same class, same Einstein radius, same mass. Second, the useful signal lives in the thin bright arcs near the Einstein radius. The rest of the image is mostly empty sky.

Axion images also store the simulated axion mass, between \(10^{-24}\) and \(10^{-22}\) eV. I used \(\log_{10}(m/\text{eV})\) as the target for a regression task. Every result in this post is on the official held-out test sets, which I only touched once, at the very end of each run.

3. Where I started

I began by building a benchmark: pretrain several SSL methods on Model I for 300 epochs, then check how well each one does on Model II with 100, 500, 1,000, 5,000 or all labels per class. I included:

  • I-JEPA, which masks parts of the image and predicts the hidden parts in feature space, using a slowly updated "teacher" copy of the network;
  • Lens-JEPA, an earlier DeepLense model that adds a lensing-inspired physics branch to I-JEPA;
  • LeJEPA, a recent method from Balestriero and LeCun that needs no teacher at all (more on this below);
  • strong supervised baselines: ResNet18, ViT, ViT-SD, Lensiformer and LensPINN.

The first result was humbling. With a frozen encoder and a linear classifier on top (a "linear probe"), the best SSL model reached only 72% on full Model II data (LeJEPA), and I-JEPA reached 60%. A supervised ResNet18 got 99.99%. The SSL features were clearly not useless, but a single linear layer could not read them out.

4. What did not work

I want to be honest about this part, because most of my summer was spent here. Each of these taught me something that ended up in the final method.

  • Dead end · linear probes Frozen probes were far too weak to judge an encoder. On the same I-JEPA encoder, a linear probe got 0.600 on full Model II, while a LoRA adapter got 0.978. Worse, the ranking changed: Lens-JEPA-Sym looked best under the probe at four of six settings, but I-JEPA beat it by more than ten points once adapters were allowed. Lesson: always evaluate a foundation model with the adaptation you will really use.
  • No gain · saliency-weighted loss (Lens-JEPA-Focus) I weighted the I-JEPA prediction loss towards patches with strong edges and curvature, hoping the model would focus on arcs. It never beat plain Lens-JEPA at any label budget. Lesson: telling the model where to look is not enough. The arc detector came back later, but as a way to pool features, not to weight a loss.
  • Partial · a global symmetry loss (Lens-JEPA-Sym) I added a loss that makes the pooled feature of an image match the pooled feature of its rotated or mirrored copy. It helped Lens-JEPA (0.866 vs 0.830 at full data with LoRA) but the gain was small. Lesson: pooling throws away which patch went where. Keeping that correspondence exact became Prior 1 of the final method.
  • Bug · a collapsed ViT-Base run My first ViT-Base I-JEPA run collapsed after two epochs: its effective rank fell from 0.023 to 0.019, meaning all images were being mapped to nearly the same feature. The cause was embarrassing: I had copied the reference learning rate of 1e-3, which was tuned for a batch of 2,048, into a batch of 128. After fixing it the run was stable, but at 3.4 minutes per epoch it needed about 17 hours for 300 epochs, so I paused it at epoch 181. Lesson: add automatic collapse checks. Every run in my final code records feature spread and effective rank each epoch and refuses to save a collapsed checkpoint.
  • Failed · Lens-Prism-JEPA, the "everything" model This was my most ambitious attempt: an 86M-parameter ViT-Base with a hard-coded rotation-equivariant tokenizer, a geometry adapter, arc-aware masking, extra morphology targets and a SIGReg term. Version 1 had a bug in spirit: its morphology target was almost the same for every image, so that loss just went to zero. After fixing that, the full 300-epoch version 3 finished, and downstream it was poor: 0.333 accuracy with full Model II data (chance level) and 0.69 with 5,000 labels per class. Lesson: too many new parts at once, and I could not tell which one broke it. Next time, one change per run.
  • Stopped early · two more variants Lens-LeJEPA+ (a 300-epoch run with an extra angular-harmonic term) stopped at epoch 29 of 300 and was never evaluated. Lens-LeJEPA-Context (masked prediction plus lensing terms) kept its pooled effective rank around 0.02–0.03 for several epochs, below my 0.04 collapse threshold, so it was stopped at epoch 21. Lesson: the simple version is the one worth finishing properly.
  • Data problem · Models IV, V and A On Models IV and V every method, supervised or not, sat at chance (about 0.34 and 0.51 accuracy, AUROC ≈ 0.50). That points to a split or label problem, not to the models, so I dropped them. For Model A, the public training release was incomplete: the shards I could download had 10,000 axion, 1,564 CDM and zero WDM images, so a fair three-class result was impossible. Lesson: when every model fails the same way, check the data before the model.

5. The idea that worked: Lens-LeJEPA

After all that, I went back to the simplest strong baseline and asked a narrower question: if I only change the loss, and put the physics in there, does it help?

The base: LeJEPA

LeJEPA is nice because it is simple. There is no teacher network, no moving average and no stop-gradient. Both views go through the same ViT, the patch tokens are averaged and passed through a small projector, and the loss has two parts: pull the two views together, and keep the cloud of all embeddings shaped like an isotropic Gaussian (a term called SIGReg). The second part is what stops the model from cheating by mapping everything to one point.

\[ \mathcal{L}_{\text{base}} = (1-\lambda)\,\mathcal{L}_{\text{inv}} + \lambda\,\mathcal{L}_{\text{SIGReg}}, \qquad \lambda = 0.02 \]

Because the base loss only sees the averaged feature, the image geometry is lost there. My two extra terms work on the full grid of patch tokens, where the geometry is still visible.

Lens-safe views

I only allow changes that a telescope could really produce for the same system: a small Gaussian blur (at most about one pixel, like a slightly different point spread function) and a little detector noise. No crop, no zoom, no rescale, since they all change the Einstein radius. No translation either, because both of my priors assume the lens is centred.

Prior 1: exact rotation and mirror correspondence

The one "big" change that is safe is rotating the detector. So before making the second view, I apply a random element \(g\) of \(D_4\), the group of the eight 90° rotations and mirror images of a square.

Here is the neat part. The image is 160 × 160 pixels and the patches are 16 × 16, so the grid is exactly 10 × 10. A 90° rotation or a mirror of the image then moves whole patches onto whole patches. Patch 7 of the rotated image contains exactly the pixels of some patch \(\pi_g(7)\) of the original. So instead of asking "is the whole image the same after rotation?", I can ask the much stronger question "does each patch token match the token of the patch it came from?":

\[ \mathcal{L}_{D_4} = \text{smooth}_{L_1}\big(\text{LN}(z_B),\ \text{LN}(z_A[\pi_g])\big) \]

This permutation is exact, not approximate. I proved it in the paper's appendix and the code checks it pixel for pixel in the unit tests. This is the difference from my earlier Lens-JEPA-Sym attempt, which only compared pooled features.

Prior 2: arc-weighted ring consistency

Prior 1 says where information should go, but not what the arcs look like, and the dark matter signal is a small change in arc shape. So I split the 10 × 10 patch grid into three rings around the centre. Inside each ring I average the tokens, but I weight every patch by a simple, label-free arc detector: the image gradient plus the Laplacian. Patches on a bright, curved arc count more than patches of empty sky.

A rotation or mirror never changes a patch's distance from the centre, so every ring maps onto itself. That means this ring descriptor should be the same for both views, and I ask for exactly that. The final loss is:

\[ \mathcal{L} = \mathcal{L}_{\text{base}} + 0.10\,\mathcal{L}_{D_4} + 0.10\,\mathcal{L}_{\text{ring}} \]

Nothing here needs a label, a lens model or an Einstein radius. And because each prior is just one extra term, turning both off gives back plain LeJEPA exactly. That gave me a clean experiment: two runs that are identical in every way (same ViT-S/16, same 100 epochs on Model I, same views, same seed, same schedule) except for these two terms.

6. Using the frozen encoder

Since linear probes were too weak (section 4), I froze the encoder and added LoRA adapters: small low-rank updates inside every linear layer of the ViT, 48 layers in total. I chose the rank on the Model II validation split only, and then fixed it for every run:

LoRA rank248163264
Validation accuracy0.9250.9530.9660.9720.9810.960

Then I compared seven adapter types, plus full fine-tuning, on the frozen Lens-LeJEPA encoder. The winner was rank-stabilized LoRA (rsLoRA). It is a one-line change: normal LoRA scales the update by \(\alpha/r\), rsLoRA scales it by \(\alpha/\sqrt{r}\), so the update does not shrink when the rank grows. At rank 32 that is 2.36M trainable parameters, 11% of the encoder.

One thing surprised me: rsLoRA is not faster per step than full fine-tuning (122 ms vs 102 ms at batch 64 on my RTX A4500), because gradients still flow through the whole frozen network. The saving is in memory and in storage: one frozen backbone plus a small adapter file per task.

What I take from this:

  • The priors help at every label budget, and most when labels are scarce: +11 points at 100 labels per class, shrinking to +1–2 points with full data. That is exactly the regime SSL is for.
  • They also beat the older lensing-specific Lens-JEPA by 13 to 30 points. To be fair, that model is much smaller (2.45M parameters vs 21.4M), so this mixes the loss with model size.
  • I-JEPA, pretrained for 3× longer, is ahead between 500 and 5,000 labels. I do not have a matched-budget I-JEPA run, so I cannot say whether that is the method or the extra compute.
  • At full data, AUROC tells a more mixed story: with plain LoRA, Lens-LeJEPA's mean AUROC (0.979) is actually a bit below LeJEPA's (0.986). With rsLoRA it reaches 0.993.
  • And supervised models, especially the physics-informed LensPINN, are still the best at every budget on this simulated data. The case for a foundation model here is label efficiency and reuse across tasks, not beating supervised accuracy.

The frozen encoder is usable (R² = 0.937 on Model II with rsLoRA), but a supervised ResNet18 is about 5× better. And here the priors do not clearly help: with the same LoRA adapter, Lens-LeJEPA is worse than LeJEPA on Model II (0.149 vs 0.121) and only better on Model III.

I think the error pattern explains why. A heavier axion has a shorter wavelength, so its vortex pattern is finer and fainter. But my objective explicitly teaches the encoder to ignore blur and noise, which act on exactly those fine scales. So the encoder has partly learned to throw away the signal this task needs, and the error is worst for the heaviest masses.

Task 3: 2× super-resolution

Here I shrink each native 64 × 64 test image to 32 × 32 and ask the model to rebuild it. A light decoder turns each patch token back into a 16 × 16 block of pixels. This is a synthetic image-reconstruction task, not real physical resolution recovery, because the dataset has no true low/high-resolution pairs.

8. The one lesson behind all of it

At first the three results looked contradictory: the priors help a lot on classification, hurt super-resolution, and do not help regression. I now think they all come from one thing.

My priors buy invariance. They teach the encoder that the orientation of the detector, and small blur and noise, do not matter. Whether that is good depends on the task:

  • A semantic task like "is this axion or CDM?" does not care how the detector was rotated. Invariance is exactly what it wants, and classification gains up to 11 points.
  • A reconstruction task needs every pixel, and an amplitude task like mass regression needs the finest texture. Invariance throws some of that away, so they lose.

I can even see this in the features during pretraining, before any downstream task. Lens-LeJEPA ends with a lower effective rank (0.164 vs 0.213) and a lower feature spread than LeJEPA: its features are more compressed. Neither run collapsed, and both lensing terms fell by about two orders of magnitude, so the priors were being satisfied, not fought.

So my practical advice is: choose the pretraining objective per task. Use the geometry-aware encoder for classification and lens finding, and the plain encoder for continuous physical quantities.

9. The code

I rewrote everything into a small, clean repository that goes with the paper. It is organised around tasks: each task says which data to load, how to split it, which head to use, the loss and the metrics, and one shared training loop does the rest. Adding a new task is one class.

lens-lejepa/
├── lens_lejepa/
│   ├── data/      # .npy loading, datasets, deterministic splits
│   ├── models/    # ViT, heads, 7 adapter types, ResNet18 / RCAN / bicubic
│   ├── ssl/       # SIGReg, lens-safe views, the two priors, the objective
│   ├── tasks/     # classification, regression, super_resolution
│   └── engine/    # pretraining loop, fine-tuning loop, evaluation
├── configs/       # one YAML per experiment, defaults = paper settings
├── scripts/       # reproduce_paper.sh, collect_results.py
└── tests/         # 63 tests, incl. the D4 proofs checked pixel by pixel
# pretrain (about 6 GPU-hours on one RTX A4500)
python -m lens_lejepa pretrain --config configs/pretrain/lens_lejepa.yaml

# classification with 100 labels per class
python -m lens_lejepa finetune --config configs/downstream/classification.yaml --set shots=100

# evaluate any checkpoint on any test set
python -m lens_lejepa evaluate --checkpoint runs/.../best.pt --test-root ../datasets/Model_III_test

To make sure the rewrite is faithful, I loaded my original checkpoints into the new code and re-ran the held-out evaluation. It gives back the paper's numbers exactly: 0.9768 accuracy for classification, 0.1001 dex for regression and 44.70 dB for super-resolution. I also checked that each loss term matches the original implementation on the same inputs.

10. Limitations and what comes next

  • Everything is simulation. Real survey images have unknown blur, blending and lens-light subtraction. The obvious next step is to pretrain on real unlabelled cutouts and test on the small set of confirmed real lenses.
  • One seed, one budget. Each encoder was trained once. Differences below about one point (for example rsLoRA vs full fine-tuning) should not be over-read.
  • The two priors were always used together. I cannot yet say how the gain splits between them, or whether 0.10 is the best weight.
  • Equivariance is learned, not built in. The ViT's position embedding is not rotation-symmetric, so the encoder is only approximately equivariant. A hard-equivariant backbone could close that gap, if it is done one change at a time this time.
  • Regression and super-resolution were only run with full data. I would like to know if the priors help them in the low-label regime.
